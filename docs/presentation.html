System Architecture

Event-Driven Microservices

Services are decoupled by domain. They communicate through Redis Streams — never by calling each other directly.

🔑 Core Patterns

  • Event-Driven: No sync service-to-service calls. Redis Streams for all state changes.
  • CQRS: Domain APIs own all writes. Gateway reads only — never writes to domain tables.
  • Transactional Outbox: Events + domain write in same Postgres transaction. Zero event loss on crash.

🛡 AI Isolation Strategy

  • AI is used for: NLP extraction, Invoice OCR, Supplier narration
  • AI is forbidden from: 3-way match decisions, supplier scoring, dock scheduling
  • All financial decisions: pure deterministic code — auditable & hallucination-proof.

Smart Dock Scheduling (CP-SAT)

  • Google OR-Tools Constraint Programming solver
  • Minimizes total weighted wait time across ALL trucks simultaneously
  • Respects door type constraints (reefer, dry van, flatbed)

  • Not FCFS — global optimization, not one truck at a time
Inbound + outbound trucks compete for the same door pool — one solver handles both

  • Quantity derived from PO qty with ±5–8% seeded variance

  • Posts Goods Receipt Note (GRN) directly to Yard API

AI Design Philosophy

AI at the Edge — Math at the Core

The most enterprise-critical design decision: AI is isolated from the decision boundary.

✅ WHERE AI IS USED

💬
NLP Requisition Extraction
Reads free-text, outputs structured JSON. Asks clarifying questions if ambiguous.
🔍
Invoice OCR (Vision API)
Reads invoice images, extracts fields with per-field confidence scores.
📝
Supplier Selection Narration
Writes human-readable explanation of why the math chose a supplier.

🚫 WHERE AI IS FORBIDDEN

  • 3-Way Match decision — pure arithmetic, fixed tolerances (2% qty, 3% price)
  • Supplier scoring — weighted formula, not a language model opinion
  • Dock scheduling — OR-Tools constraint programming, not AI inference
"By design, the AI is completely isolated from the decision boundary. AI is used as a highly capable data extractor and narrator. The actual business logic — 3-way match, dock scheduling, supplier scoring — is pure deterministic code. Our system relies on AI for usability, but falls back on math for auditability."

Graceful Degradation

If LLM API goes down: dock scheduling, 3-way matching, and payment processing continue unaffected. System reports ai_available:false — never silently degrades.

End-to-End Flow

Requisition → Payment — Fully Automated

Steps 3–8 require zero human involvement on the happy path. Humans appear only where the system should not decide alone.

INBOUND — PROCURE TO PAY
1
NLP Requisition — employee types request → LLM extracts structured intent
2
Supplier Selection — 5-factor score → PO created → supplier confirms → truck dispatched
3
Dock Scheduling — CP-SAT assigns door + time window, re-plans on delays
4
IoT Goods Receipt — dock scanner reads pallet count → GRN posted → GOODS_RECEIVED fires
5
OCR Invoice — LLM Vision reads supplier invoice → fields + confidence extracted
6
3-Way Match + Payment — PO × GRN × Invoice → within tolerance: ✅ AUTO-PAY | outside: 🚨 EXCEPTION
OUTBOUND — ORDER TO DELIVERY
  • Customer order placed → warehouse picks & stages goods
  • Same CP-SAT scheduler assigns dock door (inbound + outbound share one pool)
  • Truck dispatched → goods loaded → delivered to customer
  • No invoice, no 3-way match — asymmetry is real, not unfinished

EXCEPTION_CREATED→ alerts dashboard
Transactional Outbox Pattern

Domain write + event in same Postgres transaction. If process crashes, event survives in DB and publishes on restart. Zero event loss — guaranteed atomicity.
