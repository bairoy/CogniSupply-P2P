# Screen Documentation: YardDock — Yard Operations Dashboard

## What This Screen Is For
This is the **E2 use case screen** — the screen a **yard operator** uses to manage everything happening physically at the warehouse. It shows every truck (trailer) in the yard, which dock doors are occupied, and has the IoT camera scanner for posting goods receipts.

> **Route:** `/yard-dock`  
> **Who sees it:** Yard Operators and Admins  
> **Use case:** E2 — "Where's My Truck?"

---

## The 4 Main Components of This Screen

### 1. KPI Strip (Top Row of Numbers)
**What it shows:** Four live counters — trucks in the yard, available dock doors, average wait time, on-time arrival percentage.

**How it works:**
- Fetches from `GET /yard-status` on mount (first load).
- Listens for WebSocket events like `TRAILER_ARRIVED`, `ETA_UPDATED`, `GOODS_RECEIVED` — when any of these fire, it re-fetches and updates the numbers automatically.
- This is the **real-time reactivity** pattern: REST for the initial load, WebSocket to know *when* to re-read.

**Interview tip:** If asked "why not just poll every 5 seconds?" — Answer: Polling hammers the database on every client. WebSocket events are pushed only when something actually changes, so 10 operators watching the board all get the update at the same moment, not each at a different 5-second interval.

---

### 2. Yard Board (The Trailer Table)
**What it shows:** A live table of every trailer currently in the yard, with columns for: Trailer ID, Status, Priority, Dock Assignment, ETA, Planned Time Window, and Current Wait Time.

**How it works:**
- Each row comes from the `trailers` array in the `/yard-status` response.
- **Status badges** are color-coded:
  - `EN_ROUTE` → blue/info
  - `ARRIVED` → yellow/warning
  - `DOCKED` → green/success (currently being unloaded)
  - `DEPARTED` → neutral grey
- **Priority badges** distinguish `critical`, `high`, `normal`, `low` orders.
- **Dock Assignment column:** If a truck has a door, it shows the door ID (`DOCK-03`) as a clickable link that opens the dock detail panel. If it doesn't have a door yet, it says "Awaiting slot."
- **Planned Time Window:** Shows the CP-SAT solver's planned start/end times for the door. If the current time slips past the planned start (the truck is running late), a warning badge shows the wait.

**The action buttons** on each row change based on truck status:
- Truck is `EN_ROUTE` → shows "Gate in" button (calls `POST /trailers/{id}/arrive`)
- Truck is `ARRIVED` → shows "Berth at door" button (calls `POST /trailers/{id}/dock`)
- Truck is `DOCKED` → shows "Scan & post GRN" button (opens the IoT Scanner, described below)
- Truck is `UNLOADED` → shows "Gate out" button (calls `POST /trailers/{id}/depart`)

**Permission guard:** The action buttons only appear if the user has `PERM.yardWrite`. A finance user viewing this screen sees the data but gets a "Read-only" note where the buttons would be.

---

### 3. IoT Dock Vision Scanner
**What it shows:** A simulated camera view of a truck's load, with animated pallet detection.

**Why it exists:** The PR2 brief requirement says "simulated IoT/Computer Vision for goods receipt." Instead of just a simple button that posts a number, this widget simulates a dock camera reading the truck's cargo.

**How the animation works:**
- The "camera" view shows a dark background with a faint sensor grid overlay.
- When you click "Trigger unload scan," a green laser line sweeps across the screen (the `scan-sweep` CSS animation).
- Pallet icons light up one by one as they are "detected," with a green bounding box appearing around each one, labelled `PLT-01 97.3%`, `PLT-02 96.8%`, etc.
- The confidence percentages are generated by the `confidences()` function — they are **seeded from the trailer ID**, not random. This means the same trailer always shows the same confidence scores, so the demo is reproducible.

**How the quantity is calculated (critical interview question):**
- The old version had `SCANNED_QTY = 500` hardcoded. This was a problem because a truck carrying 1,200 units would always "scan" 500 units, which makes no sense.
- The current version uses the `scannedQty()` function with the **FNV-1a hash algorithm** seeded from the PO ID. 
- It reads `trailer.po_qty` (the PO's ordered quantity) from the API and applies a ±5–8% variance, 25% of the time.
- Most scans match the order exactly. One in four will have a slight discrepancy, which is what makes the 3-way match downstream have real `QTY_MISMATCH` exceptions to catch, not fabricated ones.
- The reason FNV-1a was chosen over a simpler hash: PO IDs are near-identical short strings (`PO-1001`, `PO-1002`). A naive `seed * 31 % N` hash barely changes between them, putting every PO on the same side of the variance threshold. FNV-1a with an avalanche pass distributes them properly.

**After the scan:** The widget calls `POST /trailers/{id}/unload` with the scanned quantity. This creates a `goods_receipts` row in the database and fires a `GOODS_RECEIVED` event, which is the signal the `match_worker` has been waiting for to run the 3-way match.

---

### 4. Dock Schedule Timeline
**What it shows:** A horizontal timeline for the next 8 hours, showing which trucks are planned for which dock doors, and when.

**How it works:**
- Fetches from `GET /yard-schedule` which returns the CP-SAT solver's output.
- Each dock door has a lane on the timeline.
- Each planned assignment is drawn as a colored block spanning its start/end time.
- Clicking a block on the timeline highlights the corresponding row in the Yard Board table above.
- The dock door cards on the left show real-time door state: `EMPTY` (grey), `RESERVED` (blue), `UNLOADING` (green), `LOADING` (purple), `BLOCKED` (red). These colors are defined in the `STATE_STYLE` constant at the top of the file.

**Interview tip on the CP-SAT solver:** The dock scheduler is not first-come-first-served. It uses Google OR-Tools to solve an optimization problem: given all trucks currently en route with their ETAs and priorities, assign each one to a door and a time window such that the total weighted wait is minimized. If you add a new truck or delay an existing one, the solver re-runs and the timeline updates. This is visible in the demo via the `delay-trailer` scenario.

## Data Flow for This Screen

```
User opens YardDock
      │
      ▼
GET /yard-status      → trailer list, dock states, KPI counts
GET /yard-schedule    → CP-SAT solver output (assignments per door per hour)
      │
      ▼
WebSocket (gateway :8003/ws) listens for:
  TRAILER_ARRIVED, TRAILER_DOCKED, TRAILER_DEPARTED,
  DOCK_ASSIGNED, DOCK_REASSIGNED, ETA_UPDATED,
  GOODS_RECEIVED, GOODS_ISSUED
      │
      ▼
On any event → re-fetch yard-status + yard-schedule → re-render

User clicks "Trigger unload scan"
      │
      ▼
Scanner animation runs (3 seconds)
      │
      ▼
POST /trailers/{id}/unload { qty_received: scannedQty }
      │
      ▼
Yard API creates goods_receipt row → publishes GOODS_RECEIVED to Redis
      │
      ▼
match_worker picks up GOODS_RECEIVED → waits for invoice → 3-way match
```
